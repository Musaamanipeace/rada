# **Rada: Build Plan, Agent Rules and Skills**

*Draft v3 · 11 November 2026\. LOCKED \= decided by the owner. PROPOSED \= suggested, awaiting confirmation. TBD \= do not build.*

## **0\. How to use this document**

*  copy sections 12–15 into the repo as AGENTS.md, CONTRIBUTING.md and .agents/skills/, and the rest into docs/.  
* **Agents:** read AGENTS.md, then only the current phase in section 11\. Never start a phase before the previous phase’s exit criteria are met. If the spec is ambiguous, log it in docs/product/open-questions.md and work on something else. Never guess, and never build TBD items.

## **1\. Product summary and glossary**

Rada is a simple, cross-platform web app (an installable PWA) for discovering things to do online and offline. Areas: **Content Suggestion** (an endless scroller, with **My Catalogues** for saved items), **Calendar**, **Portfolio**, **Watch Ads**, **Become an Advertiser**, and a public **landing page**. The experience must stay simple.

* **Category / Subcategory / Topic:** levels 1, 2 and 3 of the taxonomy (10 categories, 34 subcategories, topics in section 4).  
* **Item:** one suggested piece of content, stored as a link plus metadata, never the content itself.  
* **Variety mode:** a feed mode that mixes all categories, including ones outside the user’s interests.  
* **Interest:** a subcategory the user said they care about.  
* **Interaction:** an in-app action on an item (open, save, unsave, add to calendar, dismiss).  
* **Seed library:** the first approved items, from hand curation and the pre-launch survey.  
* **Ad:** a short story or video made by an advertiser and shown only in the Watch Ads tab. Ads are not items and never appear in the feed.  
* **Advertiser and campaign:** an advertiser is a business account; a campaign groups ads with a budget, schedule and targeting.  
* **Qualified view:** a view that meets the playback threshold in section 8.10; the unit advertisers pay for.

## **5\. Architecture and stack (PROPOSED; confirm or change in ADR-0001 during Phase 0\)**

* Next.js (App Router), TypeScript strict mode, Tailwind CSS. One modular monolith, organised by feature.  
* PostgreSQL with Prisma migrations kept in the repo. Zod validation at every boundary.  
* Auth.js with email magic link. Guests get an anonymous token in first-party storage, claimed on signup.  
* TanStack Query for server state; Zustand (persisted) for UI preferences such as filters and the thumbnails toggle.  
* @tanstack/react-virtual for the feed. Serwist for the service worker and manifest.  
* Vitest (unit), Playwright (end-to-end, plus axe accessibility checks), ESLint, Prettier, pnpm, GitHub Actions.  
* AI features sit behind an interface in src/lib/ai so the provider can change. Logging is first-party only.

## **6\. Data model (key fields; full schema in docs/architecture/data-model.md)**

* users: id, email, display\_name, role (user, reviewer, admin), region, thumbnails\_hidden, created\_at.  
* anon\_sessions: token, created\_at.  
* categories, subcategories, topics: id, parent\_id, slug, name, sort. Seeded from data/taxonomy.json.  
* items: id, title, url (unique), source\_name, description (max 280), thumbnail\_url, category\_id, subcategory\_id, topic\_id (all NOT NULL, with composite keys so the three always agree), cost (free, paid, unknown), starts\_at, ends\_at, timezone, region, status (pending, approved, rejected, expired, duplicate), origin (seed, survey, import), popularity\_count, reviewed\_by, timestamps.  
* user\_interests: owner, subcategory\_id, weight. Owner is a user or an anonymous token.  
* interactions: owner, item\_id, type (open, save, unsave, calendar\_add, dismiss), created\_at. Append-only.  
* saved\_items: owner, item\_id, created\_at. Unique per owner and item.  
* calendar\_events: user\_id, title, starts\_at, ends\_at, timezone, notes, source\_item\_id (nullable), reminder\_minutes, done\_at.  
* survey\_sessions: id, owner, consent\_at, finished\_at, claimed\_user\_id.  
* survey\_suggestions: session\_id, subcategory\_id, topic\_id (optional), title\_or\_url, pick\_type (useful, impactful, favorite), note (max 140), status, item\_id (set when approved).  
* portfolios: user\_id, username (unique), headline, intro, avatar, template, theme, visibility (draft, public, unlisted). With portfolio\_sections, portfolio\_projects, portfolio\_links: ordered, each with a hidden flag.  
* audit\_log: actor, action, target, at.  
* Ads tables: defined below; create them in Phase 6, not before.

**Ads tables (Phase 6\)**

* advertisers: id, name, website, contact\_email, status (pending, approved, suspended), free\_views\_granted, free\_views\_used, created\_at.  
* advertiser\_members: advertiser\_id, user\_id, role (owner, editor, viewer).  
* campaigns: id, advertiser\_id, name, status (draft, in\_review, approved, live, paused, completed, rejected), start\_at, end\_at, budget\_cents, daily\_cap\_cents, rate\_card\_id, created\_at.  
* ads: id, campaign\_id, format (story, video), title (max 80), description (max 280), cta\_label, cta\_url, category\_id and subcategory\_id (both required), status (draft, in\_review, approved, rejected, paused), rejection\_reason, published\_at.  
* ad\_assets: ad\_id, kind (image, video, caption, poster), storage\_key, mime, bytes, duration\_s, width, height, alt\_text. Alt text is required for images; a captions file is required for video.  
* ad\_targeting: campaign\_id, category\_ids, regions (optional).  
* ad\_reviews: ad\_id or advertiser\_id, reviewer\_id, decision, reason, checklist (JSON), at.  
* rate\_cards: id, price\_per\_qualified\_view\_cents, min\_topup\_cents, active\_from.  
* ad\_events: id, ad\_id, owner (user or anonymous token), type (impression, view\_start, qualified\_view, complete, click, not\_interested, hide\_advertiser, report), at. Append-only.  
* ad\_stats\_daily: ad\_id, day, impressions, qualified\_views, free\_qualified\_views, completes, clicks, spend\_cents. Written only by the aggregation job.  
* ledger\_entries: id, advertiser\_id, campaign\_id (nullable), type (topup, spend, refund, adjustment), amount\_cents (signed integer), ref (payment reference, manual credit note or job id, unique), at. Append-only; the balance is the sum.  
* ad\_reports: ad\_id, owner, reason, status, at.  
* viewer\_ad\_prefs: owner, hidden\_advertiser\_ids, hidden\_ad\_ids.

* POST /api/items/:id/save, DELETE /api/items/:id/save, POST /api/items/:id/dismiss, POST /api/interactions.

## **8\. Feature requirements**

**8.1 Feed.** Header with scrollable category chips (multi-select; none selected means the user’s interests), a Variety chip, toggles for Free/Paid, Upcoming and Local, and the thumbnails toggle. Card: thumbnail (hideable), title, source, category tag, cost badge, date if any, and buttons Save, Open (new tab), Not interested, plus Add to calendar on dated items only. Endless scroll with virtualization. Loading shows skeleton cards. When fresh items run out, recycle unsaved items in shuffled order; never show a dead end. Empty filter results offer a Clear filters button. Past-dated items drop out automatically. Onboarding asks for at least 3 interests and is skippable (skipping uses Variety).

**8.2 Hide thumbnails.** A toggle in the feed header and in settings. When on, no image is requested at all; cards use a compact text and category-icon layout. Applies to the feed and My Catalogues, not to portfolios. Syncs to the account; stored on the device for guests. Default: off.

**8.3 My Catalogues.** Ten category shelves that open into subcategories; empty shelves are greyed out. Un-save is allowed. Dated items keep Add to calendar. Readable offline from cache. Guest saves merge into the account on signup. Custom collections are out of the MVP.

**8.4 Calendar.** Month view on desktop, agenda view on phones. Create, edit and delete events manually or from an item. Reminders. Mark done, which becomes the activity history. ICS export first; import later.

**8.5 Pre-launch survey.** Flow: welcome with required consent; choose categories (at least one); one screen per subcategory with up to 3 suggestions or Skip; progress saved, can finish any time; summary and signup prompt (keep my picks, create an account, or delete my answers); thank-you with share link. Each suggestion has a title or link (required), a pick type (required), an optional topic and an optional note (max 140 characters). Category and subcategory come from the screen, so nothing arrives uncategorised. Nothing goes live automatically; a reviewer approves, rejects or merges duplicates. Duplicates raise popularity\_count. Copy says ‘submitted for review’, never ‘added to the library’. Limits: 3 per subcategory, one response per email, spam trap and rate limits. Target: at least 10 approved items per subcategory before launch, topped up by hand.

**8.6 Portfolio (MVP).** Profile, 1–3 projects, links, a choice of 3 templates, desktop and mobile preview, autosave, quick-start flow, completion checklist, publish and unpublish, URL \<domain\>/\<username\>, visibility draft, public or unlisted. The AI assistant only suggests headlines and descriptions; the user approves every change. Later: more sections, testimonials, custom domains, analytics.

**8.7 Landing page.** Hero with one call to action, a three-step how it works, category preview, example portfolios, an Advertise with us link, footer.

**8.8 Watch Ads (viewer side).** A voluntary, user-initiated destination (D16). Nothing in Watch Ads loads media or plays until the viewer opens the tab and taps play, and no ad appears anywhere else in Rada. While the Watch Ads switch is off (the launch default, D23), the tab is hidden and its endpoints return 404; it is turned on when the first advertiser is approved.

* **Browse:** a list of ad cards, filterable by the same ten category chips and sortable by Newest or Popular (most qualified views in the last 7 days). Each card shows an Ad label, the advertiser name, title, duration, category tag and poster image (hidden when thumbnails are off).  
* **Play:** tap to start. Sound is off until the viewer turns it on; captions are on by default; pause, skip and close are always available. No forced watching and no countdown.  
* **After playing:** a call-to-action button opens the advertiser’s link in a new tab with rel=noopener noreferrer, routed through /r/:adId so the click is counted. Play next is offered; autoplay of the next ad is off by default.  
* **Viewer controls:** Not interested, Hide this advertiser and Report on every ad. They take effect immediately and are stored in viewer\_ad\_prefs.  
* **Empty and error states:** no matches shows a Clear filters button; media that fails to load shows a retry button.  
* **Guests** can watch. Hidden ads and advertisers are kept on the device and merged into the account on signup.

**8.9 Become an Advertiser (advertiser side).** A separate area of the app for business accounts.

* **Onboarding:** sign up, verify email, submit business name, website and contact. A reviewer approves the advertiser before any campaign can go live. Each business and website gets one free allowance only.  
* **Campaign builder:** a guided flow of name and schedule, targeting (categories, optional regions), budget and daily cap, creative, then review and submit. It autosaves as a draft.  
* **Creative:** a Story is 1 to 5 images (alt text required) plus a title, description and one call to action. A Video is one file of up to 60 seconds with a poster image and a captions file. Exact file limits live in docs/ad-policy.md.  
* **Free allowance and budget:** each approved advertiser gets a free allowance of qualified views (D19). When it is used up the campaign pauses and the advertiser is emailed. After that, views are paid from a prepaid balance at the rate card. At launch the owner agrees payment directly with the advertiser and adds credit by hand; the advertiser can send a top-up request from the portal. If a payment provider is added later, it must use hosted checkout so card details never touch Rada servers. A campaign can go live only while it has free allowance left or a balance covering at least one day of spend.  
* **Status:** each campaign and ad shows its status and, if rejected, the reason. Editing an approved ad sends it back to review.  
* **Stats:** per campaign and ad, by day: impressions, qualified views, completion rate, clicks, click-through rate, free and paid views, and spend. Category breakdowns appear only above a minimum audience size. CSV export. Advertisers never see viewer identities.  
* **Controls:** pause, resume, end, duplicate a campaign, request a top-up, view the ledger.

**8.10 Ad pipelines.** Each pipeline is one module with its own tests. Steps run in order.

1. **Advertiser onboarding:** sign up, verify email, submit business details; a reviewer checks the business and website (one free allowance per business and website) and approves or rejects with a reason; on approval the free allowance is granted and the advertiser is notified by email.  
2. **Campaign lifecycle:** states are draft, in\_review, approved, live, paused, completed and rejected. Allowed moves: draft to in\_review (advertiser submits); in\_review to approved or rejected (reviewer); rejected to draft (advertiser edits); approved to live (automatic at start\_at if free allowance or balance allows); live to paused (advertiser, or automatic when the free allowance and balance run out); paused to live (advertiser, if free allowance or balance allows); live to completed (end\_at passes or budget is spent). Any other move is refused and tested.  
3. **Ad review:** an ad enters the queue when its campaign is submitted or an approved ad is edited. The reviewer works through the checklist in docs/ad-policy.md (advertiser identity clear, claims not misleading, no restricted category, captions and alt text present, link works, no tracking scripts, content informative or entertaining), then approves or rejects with a reason. Target decision time: 2 business days.  
4. **Media:** upload through a signed URL, then type and malware check, size and duration limits, poster extraction, transcoding for video (Phase 6d), then storage. An ad cannot be submitted until every asset has passed.  
5. **Serving:** the viewer opens Watch Ads and the server selects eligible ads: ad and campaign live, inside the date range, free allowance or balance available, daily cap not exhausted, matching the viewer’s chosen filters and any region target, and not hidden by the viewer. Order by viewer-interest match, then newest, with rotation so no single advertiser takes more than a set share of a page (configurable). Each ad appears once per list.  
6. **Events and billing:** the client sends batched events; the server validates and de-duplicates them (rate limit per owner; one billable view per owner per ad per 24 hours) and stores them in ad\_events. A qualified view is 5 seconds of playback or 50% of the ad, whichever comes first (configurable). A job every 5 minutes aggregates into ad\_stats\_daily, uses the advertiser’s free allowance first (free\_views\_used rises, no spend), then writes spend to ledger\_entries at the active rate, and pauses any campaign that reaches its budget or daily cap or has no free allowance and no balance left, notifying the advertiser. Billing is idempotent and reconcilable.  
7. **Reporting:** ad\_stats\_daily feeds the stats page and CSV export. Numbers on screen must equal the ledger and the free-view counter; a nightly check flags any difference.  
8. **Viewer feedback:** Not interested and Hide update the viewer’s preferences immediately. Reports go to the review queue, and an ad with several reports is paused automatically until reviewed (threshold configurable).

**8.11 Ad policy and module map.** docs/ad-policy.md (owner approval to change) holds the allowed formats and file limits, the restricted categories (draft proposal: adult content, gambling, tobacco and vaping, weapons, political and election ads, financial products with misleading claims, anything illegal in the launch region), rules on claims and disclosure, and the review checklist. Code modules: features/ads/watch (viewer UI), features/ads/advertiser (portal UI), features/ads/review (reviewer UI), lib/ads/serving, lib/ads/events, lib/ads/billing, lib/ads/media and lib/ads/policy. Other code may use a module only through its public interface.

## **9\. Ranking and privacy rules**

**Ranking v1** (weights in one file, src/lib/ranking/weights.ts). Interest match: topic 1.0, subcategory 0.7, category 0.4. Interaction signals, decaying over 30 days: save and calendar\_add \+3, open \+1, dismiss −3. Add a small popularity boost and a freshness boost for upcoming dated items. Reserve about 15% of every batch for items outside the user’s interests. Variety mode ignores interests and cycles through all ten categories. Never repeat an item within a session; never show a dismissed item again; do not show saved items in the feed.

**Privacy (hard limits).**

* No third-party analytics, ad pixels or fingerprinting. Never read browser history or cache.  
* Only first-party session storage for login and guest identity.  
* Collected: account email, stated interests, in-app interactions, survey answers. Nothing else.  
* Users can view, export and delete their data. Guest signals stay on the device until signup.  
* Location is only a region the user types or explicitly allows, never inferred silently.  
* A plain-language privacy page must ship before the survey goes live.

**Ad data rules (PROPOSED).**

* Ad events are first-party only and stored in ad\_events. No third-party SDKs, pixels or tags, and advertisers cannot add tracking scripts or pixels to ads.  
* Targeting uses only the categories a viewer chooses in Watch Ads and an optional region the viewer set. Feed interactions and interests are never used to target ads and never shared.  
* Advertisers see aggregates only. Breakdowns are hidden below a minimum audience size (default 20 qualified views). Viewer identities, emails and histories are never shared.  
* Raw ad events are kept for 90 days, after which only daily aggregates remain. Record the final period in docs/privacy.md.  
* Click redirects add only the ad id to the advertiser’s URL; no viewer identifier.  
* Rada stores no card numbers. If a payment provider is added later, card data is handled only by its hosted checkout.

## **10\. Non-functional requirements**

* **Performance:** LCP under 2.5 s on a mid-range phone over 4G; feed holds 55 fps or more with 2,000 items scrolled; set a JS budget in Phase 0 and enforce it in CI. Ad media loads only after the viewer taps play.  
* **Accessibility:** WCAG 2.2 AA, full keyboard use, reduced-motion support, axe checks in e2e tests. Ad videos need captions, a visible pause control and no autoplay with sound.  
* **Responsive:** 360 px to 1440 px. PWA installable with a passing Lighthouse PWA audit; offline shows My Catalogues and Calendar read-only.  
* **Security:** input validation, rate limiting, CSRF protection, rel=noopener on external links, role checks on every admin route.  
* **i18n:** all strings externalised; English only at launch.  
* **SEO:** only the landing page and public portfolios are indexable.

## **13\. Agent rules (copy into AGENTS.md)**

1. Source of truth, in order: docs/product/decisions.md, then this plan, then code comments. On conflict, stop and ask.  
2. Work one phase at a time. Read docs/phases/phase-N.md first and keep its checklist current.  
3. Never build, stub or mock TBD items. Phase 6 starts only after the open items it depends on (section 3\) are answered.  
4. Never guess. Log ambiguity in docs/product/open-questions.md, open a needs-decision issue, and continue with unrelated tasks.  
5. Every item must have a category, subcategory and topic, enforced in the database and in validation. Never add a path that shows uncategorised content.  
6. Privacy is a hard limit: no third-party analytics, pixels or fingerprinting, and no reading browser history or cache. Any new outbound request needs an ADR.  
7. New dependencies, services and schema changes must be named in the PR; major ones need an ADR.  
8. Small PRs (about 400 changed lines at most), conventional commits, branches named phase-N/\<topic\>. Open a PR; never push to main.  
9. Every change ships with tests: unit for logic, Playwright for flows, axe for pages. CI must pass before review.  
10. Update docs in the same PR (api.md, data-model.md, taxonomy.md, the phase checklist, CHANGELOG).  
11. Migrations are append-only. Never edit an applied migration. No destructive commands without explicit owner approval.  
12. Secrets live in environment variables only. Keep .env.example current.  
13. Accessibility and performance budgets in section 10 are requirements, not polish.  
14. Validate all input with Zod at every boundary and rate limit public endpoints.  
15. When a task matches a skill, use it and follow it exactly.  
16. End every task with a report: what changed, what was tested, what remains, open questions.  
17. Ads appear only in the Watch Ads tab, and only after the viewer taps play. Never put ads in the feed, My Catalogues, the calendar or portfolios, and never build pop-ups, interstitials, forced watching or autoplay with sound. The feed API must never return ads; a test enforces it.  
18. Viewers are never compensated for watching ads: no points, credits, rewards or perks tied to views.  
19. Money: integer cents only; the ledger is append-only and every entry has a unique reference; event handling is idempotent; never store card data (if a payment provider is added later, use its hosted checkout). Billing changes need owner review and a reconciliation test.  
20. Ad events are first-party only. Never add third-party SDKs, pixels or ad-network scripts to the app, never allow them in ad creative, and show advertisers aggregates only.  
21. Watch Ads sits behind a switch that is off by default. With it off, no ad code or media loads anywhere in the app and the Watch Ads endpoints return 404\.

Advertiser onboarding: sign up, verify email, submit business details; a reviewer checks the business and website (one free allowance per business and website) and approves or rejects with a reason; on approval the free allowance is granted and the advertiser is notified by email. Campaign lifecycle: states are draft, in\_review, approved, live, paused, completed and rejected. Allowed moves: draft to in\_review (advertiser submits); in\_review to approved or rejected (reviewer); rejected to draft (advertiser edits); approved to live (automatic at start\_at if free allowance or balance allows); live to paused (advertiser, or automatic when the free allowance and balance run out); paused to live (advertiser, if free allowance or balance allows); live to completed (end\_at passes or budget is spent). Any other move is refused and tested. Ad review: an ad enters the queue when its campaign is submitted or an approved ad is edited. The reviewer works through the checklist in docs/ad-policy.md (advertiser identity clear, claims not misleading, no restricted category, captions and alt text present, link works, no tracking scripts, content informative or entertaining), then approves or rejects with a reason. Target decision time: 2 business days. Media: upload through a signed URL, then type and malware check, size and duration limits, poster extraction, transcoding for video (Phase 6d), then storage. An ad cannot be submitted until every asset has passed. Serving: the viewer opens Watch Ads and the server selects eligible ads: ad and campaign live, inside the date range, free allowance or balance available, daily cap not exhausted, matching the viewer’s chosen filters and any region target, and not hidden by the viewer. Order by viewer-interest match, then newest, with rotation so no single advertiser takes more than a set share of a page (configurable). Each ad appears once per list. Events and billing: the client sends batched events; the server validates and de-duplicates them (rate limit per owner; one billable view per owner per ad per 24 hours) and stores them in ad\_events. A qualified view is 5 seconds of playback or 50% of the ad, whichever comes first (configurable). A job every 5 minutes aggregates into ad\_stats\_daily, uses the advertiser’s free allowance first (free\_views\_used rises, no spend), then writes spend to ledger\_entries at the active rate, and pauses any campaign that reaches its budget or daily cap or has no free allowance and no balance left, notifying the advertiser. Billing is idempotent and reconcilable. Reporting: ad\_stats\_daily feeds the stats page and CSV export. Numbers on screen must equal the ledger and the free-view counter; a nightly check flags any difference. Viewer feedback: Not interested and Hide update the viewer’s preferences immediately. Reports go to the review queue, and an ad with several reports is paused automatically until reviewed (threshold configurable). 8.11 Ad policy and module map. docs/ad-policy.md (owner approval to change) holds the allowed formats and file limits, the restricted categories (draft proposal: adult content, gambling, tobacco and vaping, weapons, political and election ads, financial products with misleading claims, anything illegal in the launch region), rules on claims and disclosure, and the review checklist. Code modules: features/ads/watch (viewer UI), features/ads/advertiser (portal UI), features/ads/review (reviewer UI), lib/ads/serving, lib/ads/events, lib/ads/billing, lib/ads/media and lib/ads/policy. Other code may use a module only through its public interface. ￼ Ranking and privacy rules Ranking v1 (weights in one file, src/lib/ranking/weights.ts). Interest match: topic 1.0, subcategory 0.7, category 0.4. Interaction signals, decaying over 30 days: save and calendar\_add \+3, open \+1, dismiss −3. Add a small popularity boost and a freshness boost for upcoming dated items. Reserve about 15% of every batch for items outside the user’s interests. Variety mode ignores interests and cycles through all ten categories. Never repeat an item within a session; never show a dismissed item again; do not show saved items in the feed. Privacy (hard limits). No third-party analytics, ad pixels or fingerprinting. Never read browser history or cache. Only first-party session storage for login and guest identity. Collected: account email, stated interests, in-app interactions, survey answers. Nothing else. Users can view, export and delete their data. Guest signals stay on the device until signup. Location is only a region the user types or explicitly allows, never inferred silently. A plain-language privacy page must ship before the survey goes live. Ad data rules (PROPOSED). Ad events are first-party only and stored in ad\_events. No third-party SDKs, pixels or tags, and advertisers cannot add tracking scripts or pixels to ads. Targeting uses only the categories a viewer chooses in Watch Ads and an optional region the viewer set. Feed interactions and interests are never used to target ads and never shared. Advertisers see aggregates only. Breakdowns are hidden below a minimum audience size (default 20 qualified views). Viewer identities, emails and histories are never shared. Raw ad events are kept for 90 days, after which only daily aggregates remain. Record the final period in docs/privacy.md. Click redirects add only the ad id to the advertiser’s URL; no viewer identifier. Rada stores no card numbers.
